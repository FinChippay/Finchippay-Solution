# Supply-Chain Verification

This document explains how to independently verify the supply-chain controls attached to
Finchippay releases (issue #644):

- **SLSA provenance** — generated by the official
  [`slsa-framework/slsa-github-generator`](https://github.com/slsa-framework/slsa-github-generator)
  reusable workflow (`generator_generic_slsa3.yml`) and attached to each release.
- **Signed release assets** — every SBOM attached to a release is signed with **cosign**
  (keyless, OIDC); the signature (`.sig`) and certificate (`.pem`) are attached alongside.
- **Signed container images + SBOM attestations** — the `ghcr.io` images are signed and carry an
  SPDX SBOM as a cosign attestation.

All of the signing/provenance steps run inside CI and use **pinned action SHAs** (see
`.github/workflows/release.yml` and `.github/workflows/docker-publish.yml`), so the code that
produces these artifacts cannot change between runs.

## 1. Verify SLSA provenance

Download the provenance asset attached to the release — it is named `attestation.intoto.jsonl`
(plus a `.sig` signature). Verify it with the official verifier:

```bash
# Install the verifier (see https://github.com/slsa-framework/slsa-verifier)
go install github.com/slsa-framework/slsa-verifier/v5/cli/slsa-verifier@latest

# Verify the provenance attestation against the release tag and the repository.
# The source ref MUST match the tag of the release you are inspecting.
slsa-verifier verify-artifact \
  --provenance-path attestation.intoto.jsonl \
  --source-uri github.com/FinChippay/Finchippay-Solution \
  --source-tag v1.2.3 \
  sbom/frontend.spdx.json
```

If the provenance is valid, the verifier prints a PASSED result and confirms the attested subject
digests match the files you downloaded.

## 2. Verify SBOM signatures (release assets)

Each release asset `<file>.json` has a companion signature `<file>.json.sig` and certificate
`<file>.json.pem`. Verify with cosign:

```bash
# Install cosign (https://docs.sigstore.dev/cosign/system_config/installation/)
# or use the CI pinned version: sigstore/cosign-installer

cosign verify-blob \
  --certificate frontend.cdx.json.pem \
  --signature frontend.cdx.json.sig \
  --certificate-identity-regexp '^https://github.com/FinChippay/Finchippay-Solution/.github/workflows/release.yml@refs/tags/v' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  frontend.cdx.json
```

The `--certificate-identity-regexp` asserts the signature was produced by the `Release` workflow
on a `v*` tag in this repository, and `--certificate-oidc-issuer` asserts it came from GitHub's
OIDC token. Both must hold for the verification to pass.

## 3. Verify container image signatures and SBOM attestations

Images are published to `ghcr.io/finchippay/` and signed keylessly on every tag push:

```bash
# Verify the image signature (keyless):
cosign verify \
  --certificate-identity-regexp '^https://github.com/FinChippay/Finchippay-Solution/.github/workflows/docker-publish.yml@refs/tags/v' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  ghcr.io/finchippay/finchippay-backend:v1.2.3

# Verify the SPDX SBOM attestation embedded in the image:
cosign verify-attestation \
  --type spdx \
  --certificate-identity-regexp '^https://github.com/FinChippay/Finchippay-Solution/.github/workflows/docker-publish.yml@refs/tags/v' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  ghcr.io/finchippay/finchippay-backend:v1.2.3

# Extract and inspect the attested SBOM:
cosign download attestation ghcr.io/finchippay/finchippay-backend:v1.2.3 | jq -r '.payload' | base64 -d
```

## How these controls are produced

| Control | Workflow | Location |
|---|---|---|
| SLSA v1.0 provenance | `.github/workflows/release.yml` | Attached to every GitHub Release |
| cosign-signed SBOMs | `.github/workflows/release.yml` | `.sig`/`.pem` alongside each release SBOM asset |
| Image signatures | `.github/workflows/docker-publish.yml` | `ghcr.io/finchippay/finchippay-{backend,frontend}` |
| SBOM attestations | `.github/workflows/docker-publish.yml` | Attached to the published images |

The weekly SBOM generation + vulnerability scan (`sbom-scan.yml`) is unchanged; these additions
provide per-release and per-image attestation on top of it.

## Troubleshooting

- **`FAILED: expected provenance materials but not found`** — the `--source-tag` (or `--source-ref`)
  must exactly match the release tag; refs are part of the provenance's verified claim.
- **`certificate identity not found`** — you are verifying against a branch push, not a `v*` tag,
  or the repo path in the regexp is wrong. Adjust the `--certificate-identity-regexp`.
- **`unsupported predicate type`** — for attestation checks ensure `--type spdx` and that the
  image actually carries an attestation (only images published via the workflow do).
